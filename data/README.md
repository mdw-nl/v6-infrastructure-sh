# Data

This folder holds every dataset the `algorithms/` run against, plus the tooling that
generates or validates per-node data. Three unrelated things in here have "datavalgen"
in the name or in play — that's the most common source of confusion, so start there.

## The three "datavalgen" things

1. **`datavalgen`** — an external CLI tool ([mdw-nl/datavalgen](https://github.com/mdw-nl/datavalgen)),
   installed as a root `pyproject.toml` dependency. It generates or validates a CSV against
   a Pydantic schema someone registers with it via Python entry points. It knows nothing
   about any specific dataset by itself.
2. **`datavalgen-model-beach`** — an external schema plugin ([MaastrichtU-CDS/datavalgen-model-beach](https://github.com/MaastrichtU-CDS/datavalgen-model-beach)),
   also a root dependency, registering the `beach_lung` model. This is the thing
   `generate_beach_data.py` (below) actually calls into.
3. **`data/datavalgen/`** — a **self-contained sub-project in this repo** (package name
   `datavalgen-test`), with its own `pyproject.toml`/`uv.lock`/`.venv`. It registers a third,
   unrelated schema (`example`: `patient_id`/`sex`/`age_at_diagnosis`/`bmi`/`charlson_ci`/
   `disease_stage`) and ships `v6-validate/`, a demo vantage6 algorithm that validates each
   node's CSV against that schema without centralizing raw values. **It has nothing to do
   with the lung1/beach/argos datasets below** — it's a standalone worked example of
   datavalgen's federated-validation side. Full details: [data/datavalgen/README.md](datavalgen/README.md).

## The three datasets

| | `lung1/` | `beach/` | `argos/` |
|---|---|---|---|
| Generated by | nothing — static files | `generate_beach_data.py` | `generate_argos_data.py` |
| Uses datavalgen? | no | yes (`datavalgen-model-beach`, for raw schema-valid rows) | no — NIfTI image files + a CSV manifest, not a flat schema-able CSV |
| Checked into git? | yes | no (gitignored, regenerate on demand) | no (gitignored, regenerate on demand) |
| Provenance | hand-crafted synthetic data, mimicking a LUNG1-like schema — **not real patient data** | synthetic, signal-injected so a centralized fit reaches a target AUC — see the script's own docstring | synthetic phantom CT/GTV images — see the script's own docstring for exactly what's realistic vs. fake |
| Default node profile | `nodes.lung1.env` (the harness default — no `--nodes` flag needed) | `nodes.beach.env` | `nodes.argos.env` |
| Consumed by | `average`, `logistic_regression`, `admm_logistic_regression`, `coxph`, `kaplan_meier`, `fed_statistics` (all by default) | `logistic_regression`/`admm_logistic_regression` as an alternative dataset (override `FEATURE_COLS`/`TARGET_COL` in `run_study.py`) | `argos_cnn` (its only usable dataset) |

See [data/lung1/README.md](lung1/README.md) for lung1's exact columns and caveats.

### `lung1/`

Four CSVs (`alpha.csv`/`beta.csv`/`gamma.csv`/`theta.csv`), one per demo organization,
~500 rows total. No generator script — these are committed as-is. They are **hand-crafted
synthetic data that mimics a LUNG1-like schema**, not a real patient dataset; treat them as
schema/plumbing fixtures, not as anything to draw clinical conclusions from.

### `beach/`

```bash
uv run python data/generate_beach_data.py
```

Calls `datavalgen-model-beach`'s `beach_lung` model to produce raw schema-valid rows
(`patient_t_stage`/`patient_n_stage`/`patient_m_stage`/`patient_overall_stage`/
`year_of_diagnosis`/`vital_status`/`interval_diagnosis_to_last_visit_in_days`/...), then
injects a tumor-risk-weighted synthetic survival outcome on top, retrying with
increasingly strong signal configs until a target centralized AUC is hit (see
`SignalConfig`/the attempt loop in `main()`). It also precomputes ready-to-use numeric/
binary columns — `t_stage_code`/`n_stage_code`/`m_stage_code`/`overall_stage_code` and
`two_year_survival` — so `logistic_regression`/`admm_logistic_regression` can run against
it without doing any encoding or outcome derivation themselves. Writes
`data/beach/beach_signal_full.csv`, `data/beach/generation_report.json`, and per-node
splits under `data/beach/splits_<n>nodes/`. Covered by `data/test_generate_beach_data.py`
(the outcome-derivation logic specifically — `uv run pytest data/`).

### `argos/`

```bash
uv run python data/generate_argos_data.py
```

Writes synthetic phantom CT/GTV NIfTI files (`data/argos/nifti/<org>/<patient>/...`) plus
a per-slice manifest CSV per org (`data/argos/<org>.csv`). No datavalgen involvement at
all — datavalgen generates/validates flat CSVs against a schema, and this dataset is
NIfTI image files, not something a flat schema can describe. Consumed only by `argos_cnn`.

## Running a generator's own tests

```bash
uv run pytest data/
```
